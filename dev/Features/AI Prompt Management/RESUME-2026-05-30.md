## 2. The "Reconcile Agenda and Tasks" capability

- Runs on ONE meeting agenda (e.g. the Unio Weekly).
- Reads: that agenda's topics + bodies + pre-brief/open-floor + prior concluded snapshots, the **included Fireflies meetings** (§ Inclusion Criteria), and the org's current Project Board items/statuses.
- Produces (for admin review, never auto-committed): updated **Pre-Brief** (per-topic this-week line + hard due dates), proposed **agenda changes** (carry/retire/add topics, update bodies), and **task create/promote** proposals (create → statusId 8 "AI Gen"; promote existing items along statuses).
- Human oversight modals; **admins (@vistamarconsulting.com) only**. (Full responsibilities in `./README.md` §2/§5; v0 prompt draft in `./prompts/refresh-agenda.v0.md` — rename to reconcile-agenda when we firm it up.)

## 6. Switchboard project findings (the predecessor system)

> Andy: "I've been doing this work through Claude in another project folder (`/Vistamar_Consulting/Switchboard`) that includes files from our previous marketing lead's SOPs. Seriously review the entire project folder." A dedicated deep-review agent ran on it — **findings integrated below.**

A dedicated agent reviewed the whole Switchboard project (README, SPEC, 36KB CLAUDE.md, decisions/memory, all 10 `contexts/`, skills, oversight, the agenda-build scripts, and the six real agenda .docx). Distilled findings:

### 6.1 What Switchboard is + THE core lesson
Switchboard is a **"practice-management brain"** — Andy's working system for running the agency, built to capture the SOPs of the **previous marketing lead, Tate Robinson** (3 yrs, replaced by Andy). **Defining principle (CLAUDE.md Directive 0b): "Claude Is The Driver, Not A Script Runner."** Every classification/routing/reconciliation/drafting judgment is made by Claude reading markdown context **live**; scripts are ONLY pure plumbing (Gmail/Fireflies pulls, docx↔markdown, PM API wrappers). Any script with a decision verb in its name is forbidden.
→ **Biggest implication for our rebuild: "Reconcile Agenda and Tasks" should be an LLM-with-rich-context task (prompt + per-org context + transcripts + board state), NOT hardcoded logic.** This is exactly why the editable per-org prompts matter.

### 6.2 How agendas were actually generated
No single "generate-agenda" skill. Claude reconciled live, then a per-meeting Python builder (e.g. `build_unio_weekly_2026-05-26.py`) **cloned the prior meeting's .docx to inherit Word styles, stripped the body, and re-emitted `add('section'/'bullet')` calls.** All intelligence (what carried forward / resolved / newly blocked / dropped) happened in Claude BEFORE the render. Bullets show reconciliation deltas ("(approved 5/20)", "52/150 returned"). The reconcile pattern: **refresh Fireflies → load prior agenda as carry-forward base → load PM board + private oversight → Claude reconciles (resolved/in-flight/blocked/new/dropped) → emit at the right altitude.** Rules used: **3-Month Resolution Rule** (questionable item >3mo old assumed resolved), recency-first (date every fact, watch "taking over"/"moving to" transition markers).

### 6.3 The agenda STYLE taxonomy → it's FOUR altitudes (strongly confirmed)
Same reconciled task-state, rendered at four altitudes for four audiences:
1. **Internal all-team touch-base** (VM Weekly Touch Base) — cross-client roll-up, organized by client, **bolded owner assignments** (`**Scot:** …`). Where Fireflies action items from all clients get reviewed + reassigned.
2. **Internal pre-meeting prep** (e.g. `BMD-pre-meeting-internal-2026-04-30.docx`) — **a FIRST-CLASS artifact distinct from the client agenda.** Priority triage (Critical/Important/Routine), tactical task lists ("Tonight (Andy)", "8 AM Thursday"), the embedded SOP/approval-map, and a **"talk track — meeting flow"** (how to run the meeting). Andy explicitly flagged this vs the client-facing doc — they're radically different docs for the SAME meeting.
3. **Client POC meeting** (Unio Weekly; GV w/ Leslie; BMD client-facing) — organized by deliverable/content pipeline; execution status + next mechanical step; the POC is the content approver.
4. **Executive biweekly** (Unio "Biweekly Marketing Updates" w/ **Clayton**) — organized by strategic initiative (Project Marina, CNN Interview, CyberKnife, Hero Banner); altitude = decisions/approvals ("pending Clayton approval"); the exec unblocks, doesn't track mechanics.

**Prime training pair:** the Unio **Weekly (5/19) literally has a top section "Pre-Brief for Biweekly (5/20)"** — the POC weekly preps + feeds the executive biweekly the next day (weekly: "claimed 6, need Camarillo + 1 provider"; biweekly abstracts to "3 providers onboarding"). → **Our per-org prompts must encode which altitude(s) a client uses + the audience; an agenda needs a style tag.**

### 6.4 Inclusion criteria (confirmed)
Join transcript↔agenda by **date (±2d) + series-name → org**; **the transcript wins** over the written agenda for routing. **Internal meetings DO feed client agendas** (the weekly→biweekly feed; the Monday VM Touch Base cross-client review; internal Scot/Cedric/Hugo prep calls). **Fireflies freshness is a HARD GATE** — stale cache was the documented #1 failure mode; re-pull before reconciling. Watch **retitled** meetings (Unio Weekly vs "Biweekly Marketing Updates" are both Unio) + **ad-hoc** ones.

### 6.5 Per-org differences (substantial — a generic prompt would produce WRONG agendas)
- **Unio** (largest, ~40%): POC David Embleton, exec Clayton Lawrence (COO). **Much work facilitates Unio's MERGER/acquisitions** — "Project Marina" (West Coast Urology → Unio Specialty Care): domain transfer, WP plugin, 3 providers onboarding (GBP claim→Rater8→R8 role), Camarillo/Oxnard. **Ownership inversions:** Andy owns reputation + Rater8/GBP provider-adds; Cedric owns press releases; Scot is the client-visible ads POC (Waseem executes). **Sequencing rule:** GBP-add blocked until the provider webpage is live. Content system-of-record = Unio SharePoint.
- **BMD**: Denni Morris = **sole approver**; **no "Did you know?" hooks**, ~1500 words; Scott owns PPC + negative reviews; VM is dashboard/matchback design partner.
- **GV**: Leslie Polley = everything-POC + approver (Andy goes direct, no Scot); Maxine edits AI drafts; **no/minimal em-dashes**; 3 blogs/mo; **Total Vision subsidiary = strategic test for a full Total Vision acquisition**.
- **ID Care**: onboarding phase, no established workflows; **May 21 DNS-swap critical deadline**; Marketing Committee (Dr. Dwivedi chair); handled by cross-client inference until patterns emerge.

### 6.6 Tate's SOPs (the inherited playbooks)

## 6c. The Internal/Public boundary (CROSS-CUTTING PILLAR — Andy 2026-05-30, deferred but critical)

The app serves **two masters at once**: facilitating client-facing meetings AND tracking Vistamar's internal work/tasks that **must never be visible to clients**. Governing rule: **Vistamar must never appear lacking or weak to a client; no Meeting Agenda can ever make us look bad as a service provider.**

- **The Project Board TAG SYSTEM is the workhorse: an `Internal` / `Public` flag.** `Internal` = nobody outside Vistamar is ever meant to see this. (Aligns with Switchboard's Layer-2 `client-internal` tag; our board already has tags.)
- **The AI (Gen) engine must be Internal/Public-aware:** route client-facing items into the client agenda; keep `Internal` items OUT of it; surface internal items only in the internal companion doc. The AI should make Vistamar look **on top of things** and let us **address underlying/remedial tasks "under the radar."**
- **Must feel ORGANIC, not heavily "gated."** The boundary should be a natural property of how content is tagged + composed, not a clunky permission wall. But it must be baked into the AI infrastructure from the start.
- **The "subsidiary internal doc"** Andy wants — secondary to the client agenda, telling the internal team what to do + how to manage things to look good — **IS the internal pre-meeting-prep artifact (§6.3 altitude #2)** + the private oversight tracking (§6.7). Strong convergence: Andy's instinct and the Switchboard predecessor independently arrived at the same artifact. Design them as one thing: the same reconciliation pass emits (a) the clean, never-weak **client agenda** (Public items only) and (b) the **internal companion** (Internal + Public, with the "how to make us look good" tactics + talk track).

**Implication for the reconcile prompt + output contract:** every reconciled item carries an Internal/Public classification; `composeAgendaHtml` (client agenda) includes only Public; the internal companion includes everything. The AI decides classification (organically, from context) but a human reviews/edits — and the safe default for anything remedial/embarrassing is `Internal`.
